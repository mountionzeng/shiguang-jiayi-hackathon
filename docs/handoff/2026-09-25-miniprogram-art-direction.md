日期：2026-09-25

基准分支：`main` = `45da79b`
参照实现：`/Users/yuandai/Documents/New project/drinking-time-local`（电脑端，`main` = `389e08ef`）

用户反馈原话：**「手机端整体生成的照片都太普通了。可以看一下电脑端的版本，但电脑端接的不是混元的图片模型，所以他们之间会出现一些误差。」**

这个判断是准确的，而且原因可以量化：

> **手机端送给图片模型的提示词只有 108 个字符，占混元 v3 上限 8192 字的 1.3%。**
> 其中美术方向只有一句硬编码常量：「纸本淡彩水彩插画，暖白色宣纸底，笔触轻柔，留白充足，画面安静。」
> 三种用途（插图 / 底图 / 封面）共用同一套措辞，不随内容、情绪、年代变化。
> 电脑端同一件事有一套分十层编译的美术判断，实测输出 2615 字。

所以「太普通」不是模型能力不够，是**没有人给模型下过美术判断**。混元 v3 的 prompt 预算有 98.7% 完全没用。

> 注意：当前 checkout 停在 `chore/migrate-enterprise-miniprogram`（`d83f1ed`，落后 main 108 个提交），
> 且带着**别人的未提交改动**。**动手前先切到 main，不要 reset / checkout / 清理那些改动。**

## 结论先说

| # | 问题 | 现状 | 改动风险 |
|---|---|---|---|
| 1 | 美术方向是**一句硬编码常量**，不随内容变化 | 三种用途各一句 `lead`，31 字 | 低 |
| 2 | **正文里的情绪、年代、生活质地全部没用上** | 提炼出来了却只当事实转述 | 低 |
| 3 | **没有质地/材料/制作痕迹的指令** | 只说「笔触轻柔」，模型默认给光滑插画 | 低 |
| 4 | 参考图**从未传给图片模型** —— 混元支持却没用 | 只进视觉模型转成文字 | 中 |
| 5 | 用户**无法表达任何美术意图** | 前端只有一个「配图」按钮 | 中 |
| 6 | 没有 `seed`，同一章重画每次都换风格 | 未传该参数 | 极低 |

**第 1、2、3 条是「太普通」的主因，三条都是纯 prompt 改动，不碰网络、不碰权限、不碰限额。**
第 4 条是现成但闲置的模型能力，单点收益最大。

## 一、手机端现在到底给了模型什么

### 1.1 全部美术方向就是这三句

`cloudfunctions/storyImages/core.js:355-375`，`STYLES` 常量：

```js
cover:        { lead: "竖版文学书籍封面画，纸本淡彩水彩与细腻宣纸纹理，暖白与柔和墨绿为基调。…",
                width: 768,  height: 1024, maxObjects: 4 },
illustration: { lead: "纸本淡彩水彩插画，暖白色宣纸底，笔触轻柔，留白充足，画面安静。",
                width: 1024, height: 768,  maxObjects: 6 },
backdrop:     { lead: "安静的纸本淡彩底图，暖白色宣纸底。上方大面积是接近纯白的宣纸留白，…",
                width: 1248, height: 832,  maxObjects: 3 },
```

插图那句 **31 个字符**，是这个产品全部的美术判断。它不随情绪、年代、题材、人物关系变化。

### 1.2 拼出来的完整 prompt 长这样

`core.js` 的 `buildImagePrompt()` 按固定顺序拼接（用测试夹具里的真实场景还原）：

```
纸本淡彩水彩插画，暖白色宣纸底，笔触轻柔，留白充足，画面安静。画面：冬天的院子里晒着被子，
竹竿横在两棵树之间。画中有竹竿、棉被、木凳。时节与光线：冬天午后的阳光。
人物以远景或局部呈现：远景中的背影。整体氛围安静温暖。
```

**108 个字符。混元 v3 的 prompt 上限是 8192 字符 —— 用掉 1.3%。**

结构是「一句风格 + 五句事实转述」。除了第一句，其余全部在描述**画什么**，
没有任何一句在说**怎么画**：没有材料、没有笔法、没有边缘处理、没有光的来源、
没有构图骨架、没有「这一张为什么要这样画」。

模型拿到这种提示词，只能交出它的平均值 —— 那就是「普通」。

## 二、最可惜的一点：信息已经提炼出来了，却被当成事实转述用掉

`cloudfunctions/storyImages/scene.js` 的场景提炼已经从正文里取出了七个字段：

| 字段 | 含义 | 现在的用法 |
|---|---|---|
| `scene` | 画面发生的地方和情景 | → 「画面：…」 |
| `setting` | 只有地点环境 | → 底图的「景物：…」 |
| `objects` | 可入画的具体物件（≤6） | → 「画中有…」 |
| `light` | 时间、季节、光线 | → 「时节与光线：…」 |
| `mood` | **两到四个字的氛围** | → 「整体氛围X。」**仅此一句** |
| `eraHint` | **明确写出的年代** | → 「时代感：…」**仅此一句** |
| `figures` | 人物（不露脸的描述） | → 「人物以远景或局部呈现：…」 |

`mood` 和 `eraHint` 是整条链路里**唯一的美术信号**，但它们各自只换来一句四个字的转述。
「整体氛围安静温暖」对图片模型几乎等于没说 —— 它不改变任何一笔怎么画。

对照电脑端 `renderGate.ts:191-207` 的 `textArtSignalBlock()`，同样的信号被编成：

```
【文本美术信号】
主情绪：怀旧
明确年代：原文未明示。不得擅自套用复古、民国、未来或其他年代造型。
生活质地：家庭内部、地方生活
叙述距离：贴近当事人的主观经验
```

差别不在提炼能力，在**提炼之后有没有人把它翻译成美术指令**。手机端缺的就是这一层。

而且电脑端多了两个手机端完全没有的维度，都是从正文正则匹配就能得到的：

- **生活质地**（`renderGate.ts:174-180`）：家庭内部 / 城市日常 / 地方生活 / 技术与系统 / 自然世界
- **叙述距离**（`renderGate.ts:186-188`）：出现「我 / 自己 / 我们」→ 贴近当事人主观经验；否则从行动与关系观察

对一个做老人回忆录的产品，「生活质地」和「叙述距离」恰恰是最该影响画面的两件事。

### 2.1 补充：把已收集的大量文字提炼成美术提示词

用户已经提供的大量叙述，不应只用来找一处可画的场景。目标是在画图前，先把与**这本书**有关的文字整理成一份简短、可核对的「美术摘要」，再把摘要翻译为媒介、笔触、年代质地、光线、构图等肯定式提示词。文字越多，越要先压缩为有证据的判断，而不是把长篇原文直接塞给图片模型。

目前能够直接接入的来源是同一本书**已保存的章节**：章节插图和底图以当前章节决定人物、地点、物件和事件，其他章节只帮助判断贯穿全书的生活质地及人物连续性；封面通读全书已保存章节，提炼共同主题和代表意象。此前采访时收集的原话、语音转写、尚未入书的记忆及 AI 整理稿如果也要使用，须先确认它们与这本书的关联、选用范围和版本；不能自动混入别的书或别的用户的内容，也不能把原话和其改写稿当作两份独立证据重复计数。**本轮代码只接入已保存章节，这些更早的素材仍是待接入范围。**

每次提炼至少形成以下字段，字段后保留简短的原文依据，便于追溯和纠错：

| 字段 | 从文字中提炼什么 | 进入图片提示词的方式 |
|---|---|---|
| 绘画媒介 | 家庭、地方、城市、自然等反复出现的生活质地 | 选择彩铅、水彩、淡墨、套印等合适的纸本媒介，并写明笔触、渗色、边缘和纸面痕迹；题材与媒介是美术判断，不假装原文指定了画材 |
| 年代依据 | 明确出现的年份、年代或历史时期及其对应章节 | 只让服装、器物、建筑等细节符合文字明确支持的年代；多段年代并存时，不给整本书强加一个时期 |
| 情绪画法 | 反复出现且未被否定的情绪 | 将「怀旧」转为擦洗和叠色，将「孤独」转为尺度和留白等可画的动作，不只复述形容词 |
| 叙述距离与母题 | 第一人称距离、重要的人物关系、反复出现的具体意象 | 决定观看距离、主体与环境的关系；每张图仍以对应章节或封面主题为事实边界 |

例：若一章写「1983 年冬天，母亲在院子里晒被子」，并在后文多次写到家中日常，摘要可以得出「家庭内部的生活质地」「1983 年」「冬季」；提示词再写「柔软彩铅与薄水彩叠在暖白纸上，棉被边缘留有铅笔底稿，院中器物符合正文写明的 1983 年」。不能因为有「旧院子」就推断民国，也不能把另一章的街道或事件画进这一章。

长章节尤其需要注意：场景模型目前只读取前 4,000 字，正文后半段若明确写出年代，仍应从**完整已保存章节**扫描并核实；来源校验也应覆盖完整文字。若出现多个不一致的时期，先保留时间跨度或空置年代提示，不替用户猜一个统一年代。

### 一个必须照搬的细节：情绪否定检测

电脑端 `renderGate.ts:161-172` 有一段 `NEGATED_EMOTION_PREFIX`：

```ts
const NEGATED_EMOTION_PREFIX = /(?:不要|并非|不是|不想|不再|并不|没有|避免|拒绝|禁止|不|without|not|no)\s*[^，。！？\n]{0,18}$/i;
```

作用是：正文写「**不想**再回到那种焦虑里」时，不把「焦虑」当成本篇主情绪。
手机端如果新增情绪推断，**这一段必须一起加**，否则会把用户明确否定的情绪当成美术方向。

## 三、缺的是「怎么画」：质地、材料、制作痕迹

手机端的 31 个字里，涉及「怎么画」的只有「笔触轻柔」四个字。
没有材料行为、没有边缘处理、没有光的来源、没有构图骨架。
图片模型在没有质地指令时的默认输出就是**光滑、均匀、无人味的插画** —— 也就是「普通」。

电脑端为此专门有一整块（`renderGate.ts:250-253`，`semanticArtBlocks()` 的第二段）：

> 【手作完成度】画面必须像真实创作者经手完成的物件，而不是光滑的 AI 渲染。
> 只选择两三种真正服务内容的制作痕迹，例如底稿、纸纤维、颜料厚薄、干刷、擦除、压印
> 或轻微套色偏差；保留有判断的边缘和局部未完成感。

还有一条风格化硬约束（`renderGate.ts:212-213`）：

> 【风格化硬约束】最终画面必须是明显风格化、具有手工媒介痕迹的原创图像，
> 不能被误认成相机照片、商品摄影、图库照片或光滑的 3D 渲染。使用可见笔触、纸面阻力、
> 颜料厚薄、套色偏差、擦除或有判断的形体简化。

**注意**：这两段的措辞不能照抄进手机端，原因见第五节。但它们指向的东西必须补上。

## 四、参考图从未真正进入图片模型（混元支持，但没接）

### 4.1 现状

`cloudfunctions/storyImages/tokenhub.js:46-53`，发给混元的请求体完整如下：

```js
body: JSON.stringify({
  model: IMAGE_MODEL,      // hy-image-v3
  prompt,
  size: `${width}x${height}`,
  revise: false,
  footnote: AI_FOOTNOTE,   // "AI生成"
}),
```

**没有 `images` 字段。**

而参考图的流向是（`flow.js:85-110`、`flow.js:162-170`）：

```
用户选的照片/插图 → storage.tempUrls() 拿到临时 URL
  → referenceAnalyzer.analyze() / analyzeCover()   ← 只进了「视觉模型」
  → 转成 {style, palette, figures, objects} 四个文字字段
  → 拼成一句「参考图的视觉连续性：画风与材质延续X；主要配色延续Y…」
  → 进 prompt
```

图片模型**从来没看到过那张图的任何一个像素**，只收到了一句二手的文字转述。

### 4.2 混元 v3 其实支持

按 TokenHub 官方文档（[Hy 生图调用指南](https://cloud.tencent.com/document/product/1823/135745)），
`hy-image-v3` 的请求参数里有：

| 参数 | 说明 |
|---|---|
| `images` | **参考图片，0~3 张，支持图片 URL 或 Base64**，png / jpeg / jpg，单图 ≤ 10MB |

而且这件事**在项目自己的设计文档里早就记着**。`docs/2026-09-13-image-management-plan.md`
第二节的能力对照表写着：「参考图（照片生成底图）：支持，`Images` 最多 3 张，Base64 或 URL，单张 < 6M」。
也就是说这不是漏查，是选了不接。

### 4.3 但这是一个有意的决定，不要当成纯粹的遗漏

`docs/handoff/2026-09-23-book-cover.md` 明确写了当时的取舍：

> 参考图经看图模型提炼视觉特征（画风、配色、可见物件），再指导生图；
> **不是保证逐像素保留或人脸身份复刻。**

把用户照片直接送进图片模型，会改变这个产品的**隐私与合规姿态**：

- 用户的真实家庭照片会离开「只做文字提炼」的边界，成为出图输入
- 涉及人脸时，「不复刻人脸身份」这条自我约束不再由架构保证，只能靠 prompt 请求
- 这个产品正在走深度合成类目提审（见 `docs/handoff/2026-09-14-route-b-enterprise-migration.md`
  与记忆里的「只走路线 B：迁企业主体、办深度合成资质」），**授权文案与提审材料可能需要同步更新**

**所以第 4 条不要和第 1–3 条打包提交。**
建议先只对「AI 自己生成的插图」启用 `images`（做同一章多张插图的风格连续性，
不涉及真人照片），真人照片那条单独找用户确认授权与提审口径。

### 4.4 收益为什么值得单独做

现在同一章重画第二张时，风格连续性靠的是「视觉模型读第一张 → 写成文字 → 图片模型再想象」
这条有损链路，`style` 字段还被 `cleanText(parsed.style, 50)` 截到 50 字。
直接传 `images` 是这条链路上唯一无损的做法，也是让一本书的插图**看起来像同一个人画的**
最省力的手段。

## 五、两端模型不同造成的「误差」：哪些能搬，哪些搬了会坏

用户已经指出「电脑端接的不是混元」。具体差在哪里、哪些措辞不能照抄，列在这里。

**两端的图片模型**：

| | 手机端 | 电脑端 |
|---|---|---|
| 模型 | 混元 `hy-image-v3`（TokenHub 直连） | Midjourney（默认）/ `gpt-image-1.5` / `flux-kontext-pro` / `flux-schnell`（均经 302.ai） |
| prompt 上限 | **8192 字符**（官方文档） | MJ 档 3500、长档 12000（`renderGate.ts` 自定义） |
| 负面提示词 | **没有这个参数** | 有（`negative` / `negativePrompt` 贯穿全链） |
| 参考图 | `images` 0~3 张（**支持但未接**） | 已接，多条路径 |

### 5.1 最重要的一条：混元 v3 没有负面提示词，而且手机端有测试在守这条

TokenHub 官方文档里 `hy-image-v3` 的请求参数只有七项
（`model`、`prompt`、`images`、`size`、`seed`、`footnote`、`revise`），
**没有 `negative_prompt`，也没有任何其他负面字段**。

手机端对此有明确的自我约束，`core.js:377` 的注释写着：

> Affirmative wording only: image models have no notion of "don't draw".

并且有两条测试在守（`tests/story-images.test.js:498` 和 `:539`）：

```js
assert.doesNotMatch(prompt, /不要|禁止|避免|不得|没有/);
```

**这意味着电脑端的大量措辞照抄进来会直接撞红测试。** 不能搬的原文举例：

- 「**不要**摄影写实、产品布光、镜头虚化和塑料质感」（`renderGate.ts:213`）
- 「**禁止**塑料般 3D 光泽、无来源泛光、过度平滑渐变」（`renderGate.ts:253`）
- 「**不得**擅自套用复古、民国、未来或其他年代造型」（`renderGate.ts:196`）
- 「**避免**把内容降格为普通摄影记录」（`renderGate.ts:340`）

**必须改写成肯定句。** 对照示例：

| 电脑端（否定式，不能搬） | 手机端应写成（肯定式） |
|---|---|
| 不要塑料般 3D 光泽、过度平滑渐变 | 颜料有厚薄，纸面有阻力，边缘保留手的判断 |
| 不要摄影写实、镜头虚化 | 形体经过概括取舍，笔触可见 |
| 不得擅自套用复古年代造型 | 服装与器物只按正文写到的年代来画 |
| 避免降格为普通摄影记录 | 画面是手工绘制的图像 |

这条不是形式要求 —— 对一个没有 negative 通道的模型，否定句会被当成**要画的内容**，
写「不要塑料感」有可能真的给你塑料感。**这是本次改动最容易踩的坑。**

### 5.2 prompt 预算：够用，但别当成无限

8192 字符对照现在的 108 字符，空间极大。但也不要滑到电脑端那个极端 ——
`renderGate.ts:80-92` 的注释记录了一次真实事故：

> 2026-08-19 SheSelf 0307：用户写了 400 字的镜头美术要求，编译出来是 2615 字，
> 他的要求只占 14.1%。剩下 86% 里，【艺术跃迁】命令模型「做一个相机拍不到的视觉决定」，
> 【艺术谱系】按关键词自动塞进一个流派…八轮重渲每次都被拉回「暗调、两个女人、油画感」
> 这个平均值。

**建议目标区间：400–900 字符。** 足够承载质地、情绪、年代、构图四层判断，
又不至于让生成性美术块淹没正文事实。电脑端为此专门加了 `authoredBrief` 开关来关掉那些块；
手机端现在还没有用户输入，不需要这个开关，但要**从一开始就守住比例**。

### 5.3 其余三个参数的现状与建议

| 参数 | 现状 | 建议 |
|---|---|---|
| `revise` | `false`（`tokenhub.js:51`） | **别动。** 官方文档说改写约耗时 11 秒；这个链路的场景提炼已经因 15 秒超时炸过一次（见 `2026-09-23-image-generation-fix.md`）。注释里的理由也成立：改写可能加进正文没说的东西。 |
| `footnote` | `"AI生成"` | 别动。官方上限 16 字符，现在占 3 个。这是合规显式标识。 |
| `size` | 三档，测试锁死 | **别放大。** 官方要求面积 ≤ 1024×1024 = 1,048,576，而 backdrop 的 1248×832 = 1,038,336，**只剩 1% 余量**。测试 `:264-265` 在守这条。 |

### 5.4 电脑端有、但这次不要搬的东西

| 电脑端机制 | 为什么不搬 |
|---|---|
| 24 条流派库 + 语义选择器 | 手机端没有评分/歧义判定，硬搬 = 随机套流派抽奖机。只借语汇（见 3.1）。 |
| 私人策展库 `art-repository/` | **catalog.json 里 99 张图全部是 `pending-analysis`，`ready` 且有 DNA 的是 0 条。** 也就是说电脑端这套目前只有 `curator-profile.json` 的五条原则在生效，情境匹配块实际输出为空。搬过来等于搬一个空壳。 |
| 拒绝信号 / 编辑偏好学习 | 依赖 `swipe_left`、语义注解这些手机端不存在的数据源。 |
| 四图探索梯度、整轮否决 | 依赖一次出四张。手机端限额是每天 10 张、每本 30 张，一次出四张会迅速烧完名额。 |

**`curator-profile.json` 的五条审美原则倒是可以借**，它们与题材无关、措辞干净，
而且其中三条正是手机端缺的那一层：

> - 优先使用可见的纸面、笔触、擦除、叠色、压印和不完美边缘，让画面保留人的制作痕迹
> - 用空间关系、尺度、留白和材料行为承载情绪，避免把抽象主题简化成现成符号
> - 让光成为空间或材料的一部分，避免无来源泛光、统一蓝调和广告式轮廓光

注意后两条含「避免」，搬之前**按 5.1 改写成肯定句**。

## 六、两个小而明显的缺口

### 6.1 用户无法表达任何美术意图

`miniprogram/pages/story-images/story-images.wxml` 全页只有按钮，**没有一个 `input` 或 `textarea`**。
用户能做的就是点「配图」，然后接受结果；不满意只能删掉重画，而重画会拿到另一张随机结果。

封面页 `story-cover.wxml` 稍好，可以选最多 3 张参考图（`toggleReference`），但同样没有文字入口。

电脑端对应的是 `renderGate.ts` 的 `userInstructions` + `intent`，而且优先级写得很硬
（`renderGate.ts:322`）：「这些是用户本人的美术指令，优先级高于你的默认想象」。

**建议**：在「配图」按钮旁加一个可选的一行输入（占位文案如「想画成什么样子（可不填）」），
值经 `cleanText` 清洗后作为**最高优先级**拼进 prompt。这是让用户摆脱「抽奖」的最直接手段。

**注意**：这条要过内容安全。`storyImages` 已经有 `createTextChecker`（`textCheck.js`）
走 `contentSecurityCheck`，用户自由输入必须过它 —— 别把一个未审核的用户输入直接送进图片模型。

### 6.2 没有 `seed`，同一章重画每次都是另一个世界

`tokenhub.js` 的请求体没传 `seed`。官方文档：`seed` 范围 [1, 4294967295]，
不传或为 0 时随机；固定 `seed` + `prompt` + `size` 才能复现。

后果是「重画一张」变成了重新抽奖 —— 用户想要的通常是「差不多但更好一点」，
拿到的却是完全不同的画风。

**建议**：`core.js` 已经有 `textHash()`（sha256 前 32 位），可以由
`familyId + storyId + chapterId` 推导出稳定 seed，让同一章的插图落在同一视觉家族里；
用户主动点「换一张」时才换 seed。这是 5 行以内的改动，风险极低，体感改善明显。

## 七、新美术标准：建议的 prompt 结构

这是本文档的交付核心。目标是把 108 字符扩到 **400–900 字符**，并且**每一层都有明确职责**。

### 7.1 六层结构

```
第 1 层  媒介与材料      ← 替换现在那句 31 字的 lead（本次改动的重点）
第 2 层  画面事实        ← 保留现状：scene / objects / light / figures
第 3 层  美术信号        ← 新增：情绪→材料行为、年代、生活质地、叙述距离
第 4 层  构图与光        ← 新增：构图骨架、光作为空间的一部分
第 5 层  手作完成度      ← 新增：制作痕迹（肯定式）
第 6 层  参考连续性      ← 保留现状；接了 images 后可简化
```

**顺序有讲究**：事实在前，美术判断在后。混元没有权重语法，靠位置区分主次。
第 3 层的输入应是上述带原文依据的美术摘要：从大量文字中先提炼，再编译为可画的媒介、年代与笔法，而非把整篇叙述附在图片提示词尾部。

### 7.2 各层写法

**第 1 层 媒介与材料**：保留「纸本淡彩 / 暖白宣纸」这个审美家族（既有用户已经习惯，
而且 `song-ink` 与它同源），但要从「一句话」变成「材料 + 笔法 + 边缘」三件事。
参考 3.1 表格里的语汇改写，例如：

> 纸本水彩与淡墨，暖白宣纸的纤维可见。笔触有轻重，颜色一层层叠上去，边缘随纸吸水自然散开，
> 留白占大面积。形体经过概括取舍，保留手的判断。

**第 3 层 美术信号**：把已有的 `mood` / `eraHint` 从「四字转述」升级为美术指令，
并补上生活质地与叙述距离（照搬 `renderGate.ts:174-188` 的正则，逻辑可直接复用）。
关键是**把情绪翻译成材料行为**，而不是只说情绪的名字：

| 情绪 | 不要只写 | 写成 |
|---|---|---|
| 怀旧 | 「整体氛围怀旧」 | 颜色像被时间洗过一层，边缘有擦洗和叠笔的痕迹 |
| 孤独 | 「整体氛围孤独」 | 人物在环境里很小，四周留出大片空，空本身是主角 |
| 温暖 | 「整体氛围温暖」 | 光从一个能指出来的地方来，落在物件上有厚度 |

这张对照表是本次改动最能决定成败的地方 —— **建议先只做三到五种情绪，做准，再扩。**

**第 4 层 构图与光**：`song-ink` 的 `composition` 与 `light` 字段可直接改写复用：
「留白占七成，主体小而偏」「没有强光源，靠浓淡分远近」。
注意底图（backdrop）已有自己的留白规则，第 4 层对它要让位，别打架。

**第 5 层 手作完成度**：按 5.1 改写成肯定句，且**一次只选两三种痕迹**，
不要把「底稿、纸纤维、颜料厚薄、干刷、擦除、压印、套色偏差」全塞进去 ——
电脑端的原文也强调「只选择两三种真正服务内容的制作痕迹」。

### 7.3 三种用途的差别

| | illustration | backdrop | cover |
|---|---|---|---|
| 第 1 层 | 完整六层 | 简化：材料 + 稀薄色彩 | 完整，另加封面构图约束 |
| 第 3 层情绪 | **是**（主力） | 弱化，底图不该抢正文 | **是**（全书主调） |
| 第 4 层构图 | 是 | **让位**给已有留白规则 | 是，上三分之一留排版区 |
| 第 5 层痕迹 | 是 | 是，但更淡 | 是 |
| 人物 | 远景/局部 | **无人物**（测试守着） | 远景/局部 |

## 八、任务拆分建议

优先级从上到下。第 1 条做完就能看出明显差别。

| # | 任务 | 范围 | 预计效果 | 风险 |
|---|---|---|---|---|
| 1 | 重写三档 `lead`，加质地/材料/制作痕迹层 | `core.js:355-375` | **最直接** | 低 |
| 2 | 情绪→材料行为对照表（先 3–5 种） | `core.js` + `scene.js` | 大 | 低 |
| 3 | 补生活质地 / 叙述距离 / 年代约束 | `core.js`，正则可抄电脑端 | 中 | 低 |
| 4 | 稳定 `seed` | `tokenhub.js` + `flow.js` | 体感明显 | 极低 |
| 5 | 用户一行美术意图输入 | `story-images.wxml/.ts` + `textCheck` | 大 | 中 |
| 6 | 接 `images` 参考图（**只对 AI 插图**） | `tokenhub.js` | 连续性最大提升 | **中，另见 4.3** |

第 1–4 条可以合成一次提交，都是纯 prompt 与参数改动。
第 5 条涉及用户输入与内容安全，单独一次。
第 6 条涉及授权与提审口径，**先找用户确认再动**。

## 九、先出样张，再定标准（这一步不要跳）

美术改动和性能改动不一样 —— **没有前后对比图，说不清有没有变好。**

1. 动手前，在同一章正文上用**现在的 prompt** 真实生成 3 张，存为基线。
2. 改完 prompt，**同一章、同一正文**再生成 3 张。
3. 挑两种差别大的题材各来一遍（建议：一段家庭内景的回忆 + 一段户外/地方生活的回忆），
   避免只在一种题材上调好看。
4. 把 6–12 张图和**两版 prompt 全文**一起放进 PR 或交给用户看。

真机确认三件事：插图、底图、封面**三档都要看**（它们共用 `buildImagePrompt`，
改一处会同时影响三处）；右下角「AI生成」标识仍在；质检没有新增「有文字 / 有乱码字」提示。

**成本提醒**：每张 ¥0.2，限额是每人每天 10 张、每本书 30 张，删掉的不返还名额。
一轮对比 6 张就用掉当天六成额度 —— **排好顺序再开始，别边改边试。**
