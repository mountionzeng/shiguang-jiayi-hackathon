## 用户定下的模型（原话整理）

- 建档案可以理解成**拉人进群聊**：大家在一个群里一起写故事，但**主笔永远是用户自己（本账号）**，权限最高。
- 故事可以有多个主人公。主人公只是故事里写的是谁，**不代表任何权限**。
- 用户决定三件事：
  1. **给谁看故事的某一部分**：按章节授权阅读。
  2. **谁可以编辑**：别人改好的版本只是**建议**，用户确认后才更新正式内容。
  3. **给谁发推荐问题**：邀请某人回答某个问题。
- 人的管理和所有邀请入口都在「记忆之家」。
- 授权对象是「故事和它的章节」，不是整本书稿（问题四会把章节从书稿移到故事里，版本跟着故事走）。

## 四种角色

| 角色 | 是谁 | 能做什么 | 不能做什么 |
|---|---|---|---|
| **主笔** | 用户自己（本账号，按 OPENID 认） | 一切：写、改、发邀请、收回、审核建议和回答 | —— |
| **读者** | 被邀请看某几章的亲友 | 只读被授权的章节 | 看其他章节、其他故事、原始记忆；改任何东西 |
| **编辑者** | 被邀请修改某几章的亲友 | 读被授权的章节，交一份「改过的版本」作为建议 | 直接改正式内容；看没授权的章节 |
| **答题人** | 被邀请回答某个问题的亲友 | 看这一个问题，交回答 | 看任何故事内容（除非另外被授权为读者） |

一个人可以同时有几种角色（例如第二章的读者 + 第三章的编辑者 + 某个问题的答题人），每一项授权单独记录、单独收回。

## 最小闭环（用户看到的样子）

1. 主笔在「记忆之家」选中一位亲友（例如「周明」），点「邀请 ta」。
2. 选邀请什么：**看**哪个故事的哪几章 / **改**哪个故事的哪一章 / **回答**一个问题（自己写，或用推荐问）。
3. 点「生成邀请」，再点「发给微信好友」，弹出微信的转发界面，选周明发出去。卡片标题只写「岱邀请你看一段家族故事」之类，**不带正文**。
4. 周明用自己的微信点开卡片，先看到一句说明：「岱邀请你（在 ta 的亲友名单里是『周明』）查看《××》第二章。你只能看到这一章。」点「确认加入」。
5. 周明只能做被邀请的那件事：读这一章、给这一章交修改建议，或者回答这一个问题。
6. 周明交上来的修改建议或回答，先经过微信内容安全检测，再进入主笔在记忆之家里的「待处理」：
   - **修改建议**：主笔看到「原文 / 建议」对照，点「采用」就存成这一章的新版本（旧版本仍在历史里）；点「不采用」只留记录。如果主笔在周明动笔之后又改过这一章，会提示「这份建议是基于旧版本写的」，由主笔决定。
   - **回答**：点「收下」，回答变成记忆库里的一段记忆（标「周明 讲述」），之后可以编进任何故事的任何一章；点「不要」只留记录。
7. 主笔随时可以「撤销邀请」或「收回」某项授权，周明下次打开立刻失效。周明也可以自己点「不再参与」。

## 设计要点

- **认人靠微信身份（OPENID），不靠昵称。** 云函数从微信上下文里拿 OPENID 来认人。页面上显示的名字，是主笔给这位亲友起的名字，**不读取对方的微信昵称或头像**，所以不用额外申请隐私接口。
- **主笔就是本账号。** 协作空间就是主笔现有的 `family_${主笔OPENID}`。别人再怎么被授权，也永远只能「建议」，正式内容只有主笔的账号能写。
- **一次性邀请码。** 每张卡片带一个随机邀请码（16 字节），数据库只存它的哈希。第一个点「确认加入」的人绑定这张邀请，别人再用同一张卡片只会看到「这个邀请已被使用」。「确认加入」用条件更新（只有状态还是「待接受」才能改），两个人同时点也只有一个成功。
- **有效期与撤销。** 邀请 7 天内有效；授权在收回之前一直有效。
- **按章节授权。** 授权对象是「某个故事（storyId）的某一章（chapterId）」。章节 id 在各个版本之间保持不变，所以主笔改了这一章，读者看到的是改过、并且通过检测的版本。
- **读者和编辑者看到的是「检测过的副本」。** 主笔发邀请、或者保存了已分享的章节时，云函数自己从数据库读出最新版本（不信任客户端传来的正文），做一次内容安全检测，通过后存一份这一章的文字副本。对方只读这份副本，碰不到主笔的原始记忆、其他章节、其他故事。没通过检测的新版本不给对方看，对方继续看上一份通过的。
- **修改建议不碰正式内容。** 编辑者的建议单独存放，并记下它基于哪一个版本。「采用」时由主笔自己的客户端把建议存成新版本（版本 id 由建议 id 推出，重试不会重复），再通知云函数把建议标成「已采用」。
- **照片只在主笔的手机上**（现有设计），所以分享只有文字，页面上会写明。
- **编辑器里标出分享状态**：已分享的章节显示「读者：周明；编辑者：林秋」，避免主笔以后往里加私密内容时忘了有人能看。

## 数据对象（全部是新集合，只有云函数能读写）

> storyId、chapterId、versionId 的字段名和来源，等问题四的数据模型定下来再对齐。

| 集合 | 放什么 | 关键字段 |
|---|---|---|
| `collab_members` | 群里的成员 | familyId、openid、personMemberId（对应主笔亲友名单里的哪一位）、status（active / left / removed）|
| `collab_invites` | 邀请记录 | tokenHash、familyId、创建者 openid、personMemberId、role（reader / editor / answerer）、target、expiresAt、maxUses=1、usedBy、status（pending / accepted / revoked / expired）|
| `collab_grants` | 某人对某一章 / 某一问题的某种权限 | familyId、openid、role、target（`{storyId, chapterId}` 或 `{questionId}`）、inviteId、status（active / revoked / left）|
| `collab_questions` | 主笔提的问题 | familyId、text、storyId（可选，问的是哪个故事）、createdAt |
| `collab_chapter_copies` | 检测通过的章节文字副本 | familyId、storyId、chapterId、title、text、sourceVersionId、checkedAt |
| `collab_suggestions` | 编辑者的修改建议 | familyId、openid、storyId、chapterId、baseVersionId、title、text、secCheck 结果、status（pending / adopted / declined）、adoptedVersionId |
| `collab_submissions` | 答题人的回答 | familyId、openid、personMemberId、questionId、text（≤500 字）、secCheck 结果、status（pending / accepted / rejected）、acceptedMemoryId |
| `collab_audit` | 操作记录 | familyId、actor openid、action、target、时间；**不存正文** |

主笔现有的集合（`families`、`family_members`、`memories`、`biography_drafts` 等）结构不改。

## 权限：全部由云函数按 OPENID 校验

新建一个云函数 `collab`，所有邀请相关操作都走它：发邀请、撤销、预览邀请、接受、读章节、读问题、交建议、交回答、列出待处理、采用 / 不采用、收下 / 不要、退出、移除成员。每个操作开头都从 `cloud.getWXContext().OPENID` 取身份：

- **主笔操作**（发邀请、撤销、审核、移除）：只能操作 `family_${自己的OPENID}` 这个空间。
- **读者**：必须有一条 active 的 reader 或 editor 授权，而且故事和章节**完全一致**。
- **编辑者交建议**：必须有一条 active 的 editor 授权，章节完全一致；建议只写进 `collab_suggestions`。
- **答题人交回答**：必须有一条 active 的 answerer 授权，问题完全一致。
- 邀请过期、被撤销、自己退出、主笔删除（软删除）了对应的亲友或故事时，一律拒绝。
- 云函数不接受客户端传来的 familyId、openid、角色或正文当作身份和权限的依据。

## 测试

自动化测试（用模拟的云数据库和模拟的微信身份，跑云函数本身）：

- **越权读取**：陌生人猜 id 来读 → 拒绝；第二章的读者读第三章、读别的故事 → 拒绝；答题人读章节 → 拒绝。
- **越权修改**：读者交修改建议 → 拒绝；第二章的编辑者给第三章交建议 → 拒绝；任何非主笔账号直接改正式内容、采用建议、撤销邀请、给别人的空间发邀请 → 拒绝；编辑者改别人的建议 → 拒绝。
- **建议不等于修改**：编辑者交了建议之后，正式内容和版本历史一个字都没变；主笔采用之后才多出一个新版本，旧版本仍在；基于旧版本的建议被标出来。
- **过期 / 撤销**：过期后接受 → 「邀请已过期」；接受前撤销 → 「邀请已撤销」；接受后收回 → 之后每一次读、交都拒绝。
- **退出**：成员点「不再参与」后读、交 → 拒绝；用旧卡片重新加入 → 拒绝。
- **一张卡片多人用**：第一个人接受成功，第二个人 → 「已被使用」；两个人同时接受 → 只有一个成功。
- **内容安全**：检测结果不是「通过」的建议或回答不保存、不给主笔看；检测接口出错时拒绝提交（宁可交不了，也不放行没检测过的内容）。
- **只存哈希**：数据库里找不到邀请码原文。

真机验收（需要两个微信号）：A 发卡片给 B，B 只能看到那一章；B 作为编辑者交的建议，A 不采用时正式内容不变；A 撤销后 B 立刻看不到；B 转发卡片给 C，C 打不开。控制台权限（第 4 步）无法用自动化测试覆盖，真机验收时用 B 的账号直接查 `collab_*` 和 A 的 `memories`，确认查不到。

## 平台合规

- **内容安全检测**：内容一旦能被另一位微信用户看到就要检测。修改建议、回答、主笔的问题、分享出去的章节文字，都用 `security.msgSecCheck`（第 2 版，带当事人 OPENID）检测。检测放在当事人刚操作的时候做（微信要求当事人两小时内访问过小程序），结果存档。
- **服务类目与主体类型（需要你确认）**：「一个用户写的内容给另一个用户看」在审核时可能被当成用户生成内容（UGC）或社交功能。**个人主体的小程序在这类功能上限制很多，可能过不了审**；企业主体也可能要补相应的服务类目。所以控制台第 1 步要先看。如果是个人主体，我会给出收窄方案（例如先只做「看一章」，暂不开放建议和回答）再请你决定。
- **用户隐私保护指引**：分享只用微信的转发卡片（`button open-type="share"` 加 `onShareAppMessage`），不读取对方昵称、头像、手机号，所以**不需要新增隐私接口**。小程序里自己的隐私说明要加一段：「你邀请的亲友只能看到你选定的章节 / 问题；他们的修改只是建议，由你决定是否采用；你可以随时收回。」被邀请人第一次打开时也先看到这段说明，点「确认加入」才算同意。
- **卡片防转发（可选加强）**：微信的「私密消息」能力（`wx.updateShareMenu` 的 `isPrivateMessage`）可以让卡片不能被转发。一次性邀请码已经挡住了「转发后别人也能用」，这一项只是再加一层。

每个阶段结束都先给你验收，不合并 main、不上传体验版、不部署云函数，除非你在对话里明确说。

## 旧的本机「阅读范围」演示怎么处理

现在的「谁可以看」只是在同一个微信账号里给档案打标记，**并不能让任何真实的人看到**。它出现在：采访结束时的「谁可以看」、记忆之家的时间线、亲友页的「档案阅读范围」、「我的」页的「已分享」计数。

建议：**阶段 5 下线这些入口，数据不删，也不自动变成真实邀请。** 理由：自动转换等于替你把内容真的发给别人，风险太大；而且旧标记对应的是本账号内的名字，不是真实的微信用户。记忆之家的亲友管理里会提示一句：「之前在本机设置过阅读范围，这不是真实分享；想让 ta 真的看到，请发邀请。」在阶段 5 之前，旧演示照常保留，页面上已经写着「不会发出邀请」。

## 开工前需要确认的默认选择

1. 读者看到的是这一章**最新的、通过检测的版本**（而不是发邀请那一刻的样子），编辑器会标出谁能看、谁能改。
2. 编辑者的修改只是建议，主笔「采用」后存成新版本，旧版本保留。
3. 收下的回答先进**记忆库**，由主笔决定编进哪个故事的哪一章，不直接改正文。
4. 邀请 7 天有效、一张卡片只能一个人用。
5. 顺序：读者（阶段 2）→ 答题人（阶段 3）→ 编辑者（阶段 4）。
6. 旧的本机「阅读范围」演示在阶段 5 下线，数据保留。
