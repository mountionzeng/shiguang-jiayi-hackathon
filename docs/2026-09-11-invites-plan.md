# 亲友邀请系统方案（问题三 · 3c）

状态：**方案待用户确认，确认前不写代码。**
分支：`fix/profiles-and-invites`（3a 已完成：旧数据归类、档案/亲友软删除、共用记忆库）。

## 一句话目标

严格的定向分享，不是公开社区：主人把「某一章」或「某一个问题」通过微信发给**一位**亲友，对方只能看到这一章或这一个问题；对方写的回答要主人同意后才进入正式内容；每一步都留记录。

## 最小闭环（用户看到的样子）

1. 主人在「亲友」里选中一位亲友（例如「周明」），点「邀请 ta」。
2. 选邀请内容：**看一章**（选哪本书、哪一章）或者**回答一个问题**（自己写，或用首页推荐的问题）。
3. 点「生成邀请」，再点「发给微信好友」，弹出微信的转发界面，选周明发出去。卡片标题只写「林岚邀请你看一段家族回忆」，**不带正文**。
4. 周明用自己的微信点开卡片，先看到一句说明：「林岚邀请你（在 ta 的亲友名单里是『周明』）查看《林岚的人生之书》第二章。只有这一章，你看不到其他内容。」点「确认加入」。
5. 周明只能看这一章（只读），或者只能回答这一个问题。
6. 周明提交的回答先经过微信内容安全检测，再进入主人的「待处理」。主人点「收下」，回答变成记忆库里的一段记忆（标「周明 讲述」），之后可以编进任何一章；点「不要」就只留记录，不进入内容。
7. 主人随时可以「撤销邀请」或「收回查看」，周明下次打开立刻看不到。周明也可以自己点「不再查看」。

## 设计要点

- **认人靠微信身份（OPENID），不靠昵称。** 周明是谁，由云函数从微信上下文里拿到的 OPENID 决定。页面上显示的名字，是主人给这位亲友起的名字，**不读取对方的微信昵称或头像**，所以不用额外申请隐私接口。
- **一次性邀请码。** 每张卡片带一个随机邀请码（16 字节随机数），数据库只存它的哈希，不存原文。第一个点「确认加入」的人绑定这张邀请，别人再用同一张卡片只会看到「这个邀请已被使用」。「确认加入」用条件更新（只有状态还是「待接受」才能改），两个人同时点也只有一个成功。
- **有效期与撤销。** 邀请 7 天内有效；主人可以随时撤销还没被接受的邀请，也可以收回已经给出的查看权。
- **按章节授权。** 授权对象是「某本书（档案 id）的某一章（章节 id）」。章节 id 在各个版本之间保持不变（沿用问题二的分章节结构），所以主人改了这一章，对方看到的是改过、并且通过检测的版本。
- **对方看到的是「检测过的副本」。** 主人发邀请、或者保存了已分享的这一章时，云函数自己从数据库读出最新版本（不信任客户端传来的正文），做一次内容安全检测，通过后存一份这一章的文字副本。对方只读这份副本，碰不到主人的书稿、记忆和其他章节。检测没通过的新版本不会给对方看，对方继续看上一份通过的。
- **照片只在主人的手机上**（现有设计），所以分享只包含文字，页面上会写明。
- **书稿编辑器里标出分享状态**：已分享的章节显示「已分享给：周明」，避免主人以后往里加私密内容时忘了有人能看。

## 数据对象（全部是新集合，只有云函数能读写）

| 集合 | 放什么 | 关键字段 |
|---|---|---|
| `collab_members` | 协作空间里的成员（空间就是主人现有的 `family_${主人OPENID}`） | familyId、openid、personMemberId（对应主人亲友名单里的哪一位）、role（viewer 只看 / contributor 可回答）、status（active / left / removed） |
| `collab_invites` | 邀请记录 | tokenHash、familyId、创建者 openid、personMemberId、target（章节：memberId + chapterId；问题：questionId）、expiresAt、maxUses=1、usedBy、status（pending / accepted / revoked / expired）|
| `collab_grants` | 某人对某一章 / 某一问题的授权 | familyId、openid、target、inviteId、status（active / revoked / left）|
| `collab_questions` | 主人提的问题 | familyId、text、memberId（针对哪本书）、createdAt |
| `collab_chapter_copies` | 检测通过的章节文字副本 | familyId、memberId、chapterId、title、text、sourceRevisionId、checkedAt |
| `collab_submissions` | 回答和补充 | familyId、openid、personMemberId、questionId、text（≤500 字）、secCheck 结果、status（pending / accepted / rejected）、acceptedMemoryId |
| `collab_audit` | 操作记录 | familyId、actor openid、action、target、时间；**不存正文** |

主人现有的 8 个集合（`families`、`family_members`、`memories` 等）完全不改结构。「收下回答」由主人自己的客户端写入记忆库（记忆 id 由回答 id 推出，重试不会重复），再通知云函数把回答标成「已收下」。

## 权限：全部由云函数按 OPENID 校验

新建一个云函数 `collab`，所有邀请相关操作都走它：发邀请、撤销、预览邀请、接受、读章节、读问题、提交回答、列出待处理、收下 / 不要、退出、移除成员。每个操作开头都从 `cloud.getWXContext().OPENID` 取身份：

- 主人操作（发邀请、撤销、审核、移除）：只能操作 `family_${自己的OPENID}` 这个空间。
- 被邀请人操作（读、答、退出）：必须在 `collab_grants` 里有一条 **active** 的授权，而且授权对象和请求的章节 / 问题**完全一致**；邀请过期、被撤销、自己退出、主人把这份档案删除（软删除）时，一律拒绝。
- 云函数里不接受客户端传来的 familyId、openid 或正文当作身份依据。

### 需要你在控制台做的设置（到时候一步步来，现在不用动）

1. **看账号主体和服务类目（只看，不改）**：打开 mp.weixin.qq.com → 设置 → 基本设置，记下「主体类型」（个人 / 企业）和「服务类目」。原因见下面「平台合规」。
2. **看现有 8 个集合的权限（只看，不改）**：微信开发者工具 → 云开发 → 数据库 → 逐个点 `families`、`family_members`、`source_records`、`memories`、`biography_drafts`、`generated_artifacts`、`assets`、`ai_tasks` → 「数据权限」，截图告诉我现在是哪一项。它们应该是「仅创建者可读写」；如果不是，我先评估改动会不会影响现有数据，再教你改。
3. **新建集合**：云开发 → 数据库 → 点「+」，依次新建上表的 7 个 `collab_*` 集合。
4. **把新集合设成客户端不可读写**：每个新集合 → 数据权限 → 选「自定义安全规则」→ 把内容换成 `{"read": false, "write": false}` → 保存。这样只有云函数能读写。
5. **部署云函数 `collab`**：在开发者工具里右键 `cloudfunctions/collab` →「上传并部署：云端安装依赖」。函数目录里会带一个 `config.json`，声明它要调用 `security.msgSecCheck`（内容安全检测）。部署前我会再提醒一次，你说「部署」我才会让你操作。

## 测试

自动化测试（用模拟的云数据库和模拟的微信身份，跑云函数本身）：

- **越权读取**：陌生人猜 inviteId / chapterId 来读 → 拒绝；有第二章授权的人读第三章 → 拒绝；有问题授权的人读章节 → 拒绝。
- **越权修改**：非主人撤销邀请、审核回答、给别人的空间发邀请 → 拒绝；被邀请人给没授权的问题提交、改别人的回答 → 拒绝。
- **过期 / 撤销**：过期后接受 → 「邀请已过期」；接受前撤销 → 「邀请已撤销」；接受后收回 → 之后每一次读都拒绝。
- **退出**：成员点「不再查看」后读 → 拒绝；用旧卡片重新加入 → 拒绝。
- **一张卡片多人用**：第一个人接受成功，第二个人 → 「已被使用」；两个人同时接受 → 只有一个成功。
- **内容安全**：检测结果不是「通过」的回答不保存、不给主人看；检测接口出错时拒绝提交（宁可提交不了，也不放行没检测过的内容）。
- **只存哈希**：数据库里找不到邀请码原文。

真机验收（需要两个微信号）：A 发卡片给 B，B 只能看到那一章；A 撤销后 B 立刻看不到；B 转发卡片给 C，C 打不开。

控制台权限（第 4 步）无法用自动化测试覆盖，真机验收时用 B 的账号在开发者工具里直接查 `collab_*` 和 A 的 `memories`，确认查不到。

## 平台合规

- **内容安全检测**：内容一旦能被另一位微信用户看到就要检测。被邀请人的回答、主人的问题、分享出去的章节文字，都用 `security.msgSecCheck`（第 2 版，带当事人 OPENID）检测。检测放在当事人刚操作的时候做（微信要求当事人两小时内访问过小程序），结果存档。
- **服务类目与主体类型（需要你确认）**：「一个用户写的内容给另一个用户看」在审核时可能被当成用户生成内容（UGC）或社交功能。**个人主体的小程序在这类功能上限制很多，可能过不了审**；企业主体也可能要补相应的服务类目。所以控制台第 1 步要先看。如果是个人主体，我会给出收窄方案（例如先只做「看一章」，并去掉回答功能）再请你决定。
- **用户隐私保护指引**：分享只用微信的转发卡片（`button open-type="share"` 加 `onShareAppMessage`），不读取对方昵称、头像、手机号，所以**不需要新增隐私接口**。小程序里自己的隐私说明要加一段：「你邀请的亲友只能看到你选定的那一章 / 那一个问题；你可以随时收回。」被邀请人第一次打开时也先看到这段说明，点「确认加入」才算同意。
- **卡片防转发（可选加强，放到阶段 4）**：微信的「私密消息」能力（`wx.updateShareMenu` 的 `isPrivateMessage`）可以让卡片不能被转发。一次性邀请码已经挡住了「转发后别人也能用」，这一项只是再加一层。

## 旧的本机「阅读范围」演示怎么处理

现在的「谁可以看」只是在同一个微信账号里给档案打标记，**并不能让任何真实的人看到**。它出现在：采访结束时的「谁可以看」、记忆之家的时间线、亲友页的「档案阅读范围」、「我的」页的「已分享」计数。

建议：**阶段 4 下线这些入口，数据不删，也不自动变成真实邀请。** 理由：自动转换等于替你把内容真的发给别人，风险太大；而且旧标记对应的是本账号内的名字，不是真实的微信用户。亲友页会提示一句：「之前在本机设置过阅读范围，这不是真实分享；想让 ta 真的看到，请发邀请。」在阶段 4 之前，旧演示照常保留，页面上已经写着「不会发出邀请」。

## 需要你确认的默认选择

1. 对方看到的是这一章**最新的、通过检测的版本**（而不是发邀请那一刻的样子），编辑器会标出「已分享给谁」。
2. 收下的回答先进**记忆库**，由你决定编进哪一章，不直接改正文。
3. 邀请 7 天有效、一张卡片只能一个人用。
4. 先做「看一章」（阶段 2），再做「回答问题」（阶段 3）。
5. 旧的本机「阅读范围」演示在阶段 4 下线，数据保留。
