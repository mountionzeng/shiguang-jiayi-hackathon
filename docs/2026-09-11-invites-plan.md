# 亲友邀请系统（问题三 · 人与权限）

状态：**已上线，房间级别。** 本文件原本是一份按「故事 → 章节」精细授权的方案稿；实际实现走了更简单的路径，下面记录现状和用户明确做过的取舍，避免以后又把没做的精细方案当成待办重新捡起来。

## 现状（main 上已有）

- 邀请粒度是**整个家庭房间**：对方接受邀请后，能看到这个房间里公开的内容，不是挑着某个故事的某几章给。
- 相关代码：
  - 页面 `miniprogram/pages/invite/`（生成邀请海报/邀请码、接受邀请）
  - 服务 `miniprogram/services/familyInviteService.ts`（`createFamilyInvitation`、`createFamilyInvitationCode`、`loadFamilyInvitation`、`acceptFamilyInvitation`、`loadSharedFamilyRoom`、`loadJoinedFamilyRooms`、`submitSharedContribution`）
  - 云函数 `cloudfunctions/familyInvite/`（`core.js` + `index.js`，服务端按微信身份校验）
- 「家人和朋友」名单页（加人、删人、恢复「最近删除」）在 `miniprogram/pages/profiles/`。

## 用户 2026-09-14 的决定

问：现在的邀请是房间级别的，对方进来就能看到房间里公开的内容，要不要再做「按章节挑着给某个人看」这种更细的权限？
答：**先不做，房间级别够用。**

所以下面「原方案」里"按章节授权阅读""编辑者交建议、主笔采用""按故事拉群"这些设计**不再是待办**，不需要对齐问题四的故事/章节字段来实现它们。如果以后用户又想要更细的权限，再重新评估，到时候故事结构已经是「问题四」定的「故事 → 章节 → 版本」，字段应以那时的实际模型为准，不要照抄下面的旧设计。

## 用户定下的模型（原话整理，历史记录）

- **一个故事一个群。** 每个故事自己拉人、自己定主人公（主人公可以是任何人）。大家在这个群里一起写这个故事，但**主笔永远是用户自己（本账号）**，权限最高。
- 主人公只是故事写的是谁，**不代表任何权限**。
- 用户在每个故事里决定三件事：
  1. **给谁看这个故事的某一部分**：按章节授权阅读。
  2. **谁可以编辑**：别人改好的版本只是**建议**，用户确认后才更新正式内容。
  3. **给谁发推荐问题**：邀请某人回答某个问题。
- **邀请和按章节授权都挂在故事上**，不挂在「档案」或人身上。界面上不再用「档案」这个词，只说「人」。
- 聊天页没有「谁在讲」：这台手机上讲的都记在账号主人名下。一段记忆可以放进多个故事，写没写进书由故事的章节引用推导出来（问题四负责）。
