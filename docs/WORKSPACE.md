## 开始开发

1. 从本仓库根目录确认 main、远端与当前工作区状态。
2. 执行 `npm run workspace:check`，检查代码是否偏离已记录云端源码。这个命令不联系云端，不代表实时线上状态。
3. 新功能从当前 main 创建独立工作树。继续记忆共创功能时使用上表唯一的在研分支，先读其交接文档。
4. 同一时间只允许一个任务操作微信开发者工具和共享云环境。其他任务先在独立工作树开发、测试。
5. 局部测试使用 `npm run test:files -- tests/具体文件.test.js`；交付前执行 `npm run check`。

本机 Node 为 24，当前云端函数运行时为 Nodejs16.13。云函数代码需兼容云端运行时；本地测试通过不等于真机流程通过。各工作树目前可以从仓库根目录解析相同锁文件版本的依赖；调整依赖前应检查对其他在研副本的影响。

## 部署与回退

- 先提交和检查，禁止部署未提交工作区。标准部署脚本会检查 main 祖先关系和 AppID/环境映射。
- 默认部署清单仍由 `deploy/wechat-cloud.manifest.json` 控制；危险维护函数仍不允许普通部署。
- `deploy/observed-cloud-baseline.json` 保存核对时间、环境和逐文件 SHA256，只代表当时下载到的业务源码；不包含密钥、环境变量、依赖包或完整客户端发布信息。
- 标准脚本结果输出源提交、分支、AppID、云环境、函数列表与核验时间，部署人应保留结果。Active 只是运行状态，不能取代源码和功能验证。
- 如果云端有未进主线的修复，先下载留存并核对，禁止直接用旧 main 覆盖。正式客户端上传与云函数部署是不同的发布步骤。

## 找回历史成果

本次备份位于仓库同级的 `shiguang-workspace-backups/environment-repair-20260926-181231`，保留：

- Git bundle：整理前历史与包含恢复点的历史。
- `manifest.json`、每份工作树的改动压缩包、差异补丁及逐文件 SHA256；全部压缩包已逐文件校验。
- `recovery-points.json`：原工作树路径、分支、备份编号与 `refs/archive/environment-20260926/*` 恢复引用。
- `active-checkpoint.json`：在研记忆编辑工作保存提交 `046fb14` 的文件清单。
- `cloud-current.json` 与 `cloud-current/`：本次下载到的云端源码及校验值。
- `archived-worktrees.json`：历史工作树的新旧位置、分支和锁定状态。

恢复时在新的隔离工作树上使用记录的原始 HEAD，再应用对应 `refs/archive/...`；不在 main 直接恢复 stash，也不要根据会移动的 stash 序号猜测目标。归档工作树需要先明确恢复用途、解除锁定并移回合适路径。原有 stash 及备份均未删除。
