# 故事分享、亲友共创与跨端编辑需求

## Summary

让用户将故事或章节分享给亲友、制作社交图文卡片，并在手机与网页之间继续编辑同一个故事。亲友可以按授权阅读、共同编辑原稿，或保存独立副本加入自己的经历；副本保留来源及原内容的传播限制。

本文件记录已确认的产品范围，不代表功能已经实现或上线。

---

## Problem Frame

同一段往事对不同亲友有不同意义：有人只想读，有人希望补充，有人希望把它收入自己的故事。如果只有一个“分享”开关，就无法区分观看、修改原稿、保存副本和公开传播，容易泄露私人内容或误改原作者的故事。

用户还希望手机记录后换到电脑继续编辑，而不是在两个端各自维护一份内容。现有电脑入口的传输能力不能直接证明跨端双向编辑已经成立。

---

## Actors

- A1. 故事所有者：创建故事，选择分享范围、接收者及权限，决定是否收录亲友回传的记忆。
- A2. 受邀阅读者：仅阅读授权内容；其他行为需另行授权。
- A3. 副本创作者：将授权内容收入自己的故事，改写、补充经历，并在许可范围内分享或回传。
- A4. 共同编辑者：修改被授权的原故事或章节，不因此自动获得复制或传播权。
- A5. 跨端编辑用户：通过微信身份在手机与网页之间继续编辑；可能同时属于上述角色。

---

## Key Flows

- F1. 邀请亲友阅读或共同编辑
  - **Trigger:** A1 选择一个故事或章节并发起邀请。
  - **Actors:** A1、A2、A4。
  - **Steps:** 选择范围与权限 → 接收者核实身份 → 进入授权内容 → 阅读或提交修改。
  - **Outcome:** 仅可操作授权范围；身份不符、权限被撤销时拒绝进入或保存；编辑冲突保留修改供处理。
  - **Covered by:** R1、R2、R3、R4、R5、R10。
- F2. 亲友保存、补充与回传
  - **Trigger:** A3 收到允许改写副本的章节。
  - **Actors:** A1、A3。
  - **Steps:** 选择新故事或已有故事 → 保存独立副本 → 加入自己的经历或照片 → 按授权分享，或把自己的新增记忆回传 → A1 选择是否收录。
  - **Outcome:** 原稿不被副本编辑影响，来源与限制保留；不允许传播时阻止包含受限内容的对外分享，可单独发送自己的新增经历。
  - **Covered by:** R6、R7、R8、R9、R11。
- F3. 手机故事到网页继续编辑
  - **Trigger:** A5 在手机选中故事，希望换电脑编辑。
  - **Actors:** A5。
  - **Steps:** 选择故事 → 网页通过微信身份确认 → 打开对应故事 → 编辑保存 → 回手机查看更新。
  - **Outcome:** 两端编辑同一逻辑故事；身份不符拒绝访问，保存失败或冲突不能显示为成功。
  - **Covered by:** R3、R10、R12、R13。
- F4. 制作社交图文卡片
  - **Trigger:** 有公开发布权限的用户选择故事内容。
  - **Actors:** A1、获相应授权的 A3 或 A4。
  - **Steps:** 选择摘录及图片 → 检查公开发布权限 → 预览标题、正文与署名 → 导出图片 → 用户自行发布。
  - **Outcome:** 导出内容仅含所选且可公开发布的材料；无权限时说明原因，不导出受限内容。
  - **Covered by:** R4、R7、R8、R14。

## Requirements

**授权与隐私**

- R1. 所有者可按接收者、故事或指定章节授予权限。仅授权章节时，不得暴露其他章节、未授权照片或私人素材。
- R2. 提供“仅阅读”“可改写副本”“共同编辑”常用预设，默认仅阅读。复制与修改原稿是不同能力，可组合授权；共同编辑不得隐含复制权。
- R3. 私密邀请需核实接收者身份，获得链接不等于获得权限。具体认领方式留给技术方案，但必须避免误认领造成内容泄露。
- R4. “转给亲友”与“公开发布”分别授权，不能由阅读、复制或编辑权限推导出来。转发不能放大权限，接收者不能自行授予其未获准授予的权利。
- R5. 所有者可撤销原内容的阅读和编辑授权。已合法收入个人故事的独立副本仍保留，不因原稿删除或访问权撤销而自动删除；保留副本不代表解除传播限制。

**独立副本与记忆往返**

- R6. 允许复制时，接收者可创建自己的新故事，或将内容作为章节收入已有故事；可以编辑副本、加入自己的经历与照片，不修改原稿。保存后原稿的后续修改不静默覆盖个人副本。
- R7. 副本保留来源与作者归属信息。包含原内容的副本继续受原内容传播限制约束；改写、收入新故事或再次复制不构成解除限制的理由。
- R8. 亲友自己新增的经历可单独分享；包含禁止传播的原内容时，不可对外分享或公开导出。整章或整本包含多个来源时，不能借合并绕过任一来源限制。产品只能约束产品内操作，不承诺阻止截图、手工复制或追回已流出文件。
- R9. 亲友可将自己的新增记忆回传，由原用户选择收录为新内容，不自动覆盖原稿。含他人来源的回传内容仍需满足相应传播权限。
- R10. 原稿共同编辑与跨端编辑均保留修改历史；多人或两端同时提交时，不静默覆盖他人修改，需保留本次内容并告知用户冲突。
- R11. 同一来源、同一版本的重复接收或重复操作，不自动新增重复记忆；有新增经历的回传不应被当作无变化重发而丢弃。

**跨端与社交发布**

- R12. 用户在手机选定故事后，可在网页通过微信身份进入对应故事继续编辑；不得混入其他账号或故事。微信身份确认的具体可行接入方式需技术核实，不把现有一次性登录码等同于已具备官方网页微信扫码登录。
- R13. 两端面对同一逻辑故事，成功保存的编辑能在另一端重新打开或刷新后看到；清晰区分未保存、保存成功、失败与冲突。权限检查在网页和小程序保持一致。
- R14. 第一版社交发布支持图文卡片：用户选择摘录，可搭配照片或插图，预览标题、内容与必要署名后导出图片，自行发布。不得将私密邀请链接或未选中的私人内容附带到公开卡片中。

## Acceptance Examples

- AE1. **Covers R1、R2、R3.** 小明只邀请姐姐阅读第三章；姐姐完成身份核实后能读第三章，不能查看其他章节或修改原稿。其他人拿到邀请链接不能直接看到正文。
- AE2. **Covers R2、R4.** 姐姐被授予共同编辑但没有复制、转发或公开发布权限；她能保存原稿修改，但不能保存个人副本或生成对外分享材料。
- AE3. **Covers R6、R7.** 姐姐将第三章收入自己的故事并加上童年照片；小明的第三章不变，姐姐的章节仍显示来源。小明后来修改原稿，不覆盖姐姐的副本。
- AE4. **Covers R4、R7、R8.** 小明允许复制但禁止转发；姐姐补充两段经历后，仍不能把含小明原内容的章节或整本书分享出去。单独选择姐姐新增的经历且不含受限原内容时，可以分享。
- AE5. **Covers R4、R8、R14.** 某章获准转给亲友但未获准公开发布；不能因此导出该章的社交图文卡片。另一本书合入该章，也不能绕过限制。
- AE6. **Covers R5、R7.** 姐姐已合法保存副本后，小明撤销原稿访问或删除原稿；姐姐不能继续进入或编辑原稿，自己的副本仍在，原有禁止传播限制仍在。
- AE7. **Covers R9、R11.** 姐姐把新增记忆发回，小明预览后选择收录；拒绝收录不改变原故事。无变化的同一版本重复发送或重复点击接收，不自动产生第二条；真正新增的经历仍可收录。
- AE8. **Covers R10、R12、R13.** 手机和网页同时编辑同一版本；一端先保存，另一端再提交时提示冲突并保留本次修改，不覆盖前一次保存。
- AE9. **Covers R3、R12、R13.** 用户从手机选择故事甲，在电脑完成身份确认后进入甲而非故事乙；网页成功保存后手机重新打开可看到更新。错误账号不能通过更换故事标识读取甲。
- AE10. **Covers R5、R10、R13.** 共同编辑者打开页面后被撤销权限，再提交时不能保存；网络失败时也不能显示保存成功，并保留本次尚未保存的文字。
- AE11. **Covers R4、R14.** 所有者导出自己可公开发布的摘录卡片，预览与导出内容一致；未选中的章节、私人素材和私密邀请链接不出现在图片中。

## Success Criteria

- 所有者无需理解技术术语，即可区分修改原稿、保存副本、转给亲友和公开发布。
- 完成“邀请 → 收入个人故事 → 补充 → 回传 → 选择收录”的完整验证，原稿、副本和来源保持正确。
- 手机选中的故事可在网页继续编辑并回手机查看，跨账号、越章节访问与冲突覆盖测试均不通过越权操作。
- 无权限的转发和导出在两端都被拒绝，而非仅隐藏按钮。
- 实施计划逐项对应 R1–R14 与验收场景，明确技术验证门槛，不把未知平台能力写成已有能力。

---

## Scope Boundaries

- 第一版不做视频形式的社交发布，也不自动登录第三方社交平台代发。
- 不要求多人实时显示光标或逐字同步；不静默覆盖、保留历史仍是必需。
- 不将原有声音克隆、音视频渲染作为本功能的前置条件。
- 不把手机到电脑的单次快照导入当作已完成双向编辑。
- 不承诺技术阻止所有截图、手工抄写或撤回已发布到外部平台的图片。
- 本需求确认不授权部署、账号迁移、付费服务调用或对外发布用户内容。

---

## Key Decisions

- 用户于 2026-09-18 选择“原内容仍受限制”：允许保存或改写不代表允许再次传播；自己的新增经历可单独分享。
- 用户确认复制权、原稿编辑权、亲友转发权、公开发布权分别控制；私密邀请必须核实接收者身份。
- 用户确认先做图文卡片、跨端继续编辑及按权限共创，视频与自动代发暂不纳入。
- 建议实施顺序（不是已完成的技术计划）：先验证身份和授权基础，再打通章节分享/副本回传与共编，随后跨端编辑，最后社交导出。网页身份可行性应提前验证，避免晚期阻塞。

## Dependencies / Assumptions

- 延续独立故事边界，参考 `docs/brainstorms/2026-09-17-independent-story-books-requirements.md`；本文件不重置既有故事或音频计划状态。
- 已查看的 `cloudfunctions/storyBooks/index.js` 根据当前微信身份确定记录空间；不能直接把他人的故事标识传入就当作已建立共创授权。
- `miniprogram/services/drinkingTimeAccount.ts` 和 `cloudfunctions/drinkingTimeBridge/core.js` 中可见故事快照与一次性登录码流程。这不是本需求全部跨端能力已经存在的证明。
- 桥接文档 `docs/integrations/drinking-time-bridge-contract.md` 标为草案；规划需逐项核对代码、契约与实际部署，不沿用文档中的历史部署状态作当前结论。
- 用户后续可能迁移小程序账号。技术方案必须评估跨端身份、邀请与归属的迁移影响；不能仅因旧账号只有一位用户而忽略其故事、副本与权限关联。

## Outstanding Questions

### Resolve Before Planning

- 无阻止技术规划的范围问题；规划中发现新的用户可感知权利变化时，应回到产品确认，不自行放宽权限。

### Deferred to Planning

- [Affects R3、R12][Needs research] 核实当前账号可用的网页微信身份确认方式、相关平台资格及后续账号迁移限制；不可用时提出清晰替代方案供用户选择。
- [Affects R1–R5、R13][Technical] 核对现有亲友邀请、存储、图片访问及电脑侧授权，确定一致的权限检查与撤销生效验证方案。
- [Affects R6–R9、R14][Technical] 如何在改写、再次复制、合并、图文导出中保留来源与限制，并可靠分离用户自己的新增内容；无法证明独立时不能假定原限制失效。
- [Affects R3、R4、R7][Technical] 制作授权生命周期验收清单，明确私密邀请认领、转发后再授权、传播权限后续变更的行为。若方案需要新增产品规则，实施前回到用户确认。
- [Affects R10–R13][Technical] 核实双端故事标识、照片可用性、版本历史、保存冲突与重复回传检测，形成端到端验证计划。
- [Affects R1、R6、R10][Technical] 区分授权原稿的当前版本与个人副本的保存版本；规划需说明分享阅读更新行为，不将这两者混用。
