# 就地小忆需求

## Summary

用户的原话：**「聊天功能和写作功能的结合。小忆的 logo 随时出现在界面上。
如果用户在写作的过程中写不出来了，点击小忆，小忆可以自动识别到用户写作的内容，
调出对应的对话或问题。这个结合在编辑记忆和编辑文章的时候都会有。」**

这不是给两个界面各做一套 AI，而是**一个机制在两个编辑场景里复用**：
用户卡住 → 点小忆 → 小忆读当前正在写的内容 → 给一个贴着这段内容的问题 →
用户说出来的话可以变成正文。

用户明确要求时，小忆也可以代写 —— **但顺序固定**：先在选中位置问一个问题，
拿到用户的回答，再把这个回答整理成一段正文交给用户。
**代写的原料只能是用户刚说出的话，不是小忆的想象。**
（2026-09-27 用户修正：「他可以写，只是一个按钮的问题。」
最初版本把「不写正文」定为硬门禁，过严；真正的分界不在「能不能写」，
而在「写的内容从哪来」。）

关键是「卡住」这个时刻。现在的产品形态是把对话和写作分成两件事：
`interview` 页负责聊，`book` 页负责写。卡住的人必须离开正文、去另一个页面、
再想办法把聊出来的东西搬回来。**这个搬运动作就是放弃的地方。**

**好消息是地基几乎都在**，这一轮主要是接线而不是新建：

| 已有的东西 | 在哪 | 本需求怎么用 |
|---|---|---|
| 取当前选区的按钮模式 | `book.ts:767` `openShareSelection`，用 `catchtouchstart` + `getSelectionText` 抢在失焦前读 | 小忆按钮照抄这个取选区方式 |
| 「提议→对照→接受」的数据结构 | `PendingChapterRevision` / `ChapterEdit`（`insert`/`delete` + anchor + `pending\|accepted\|rejected`） | AI 产出的正文走这条，不直接改写 |
| 对话能力与 12 条约束 | `cloudfunctions/chatInterview`，2026-09-27 已加「必须贴着最新一句话」 | 就地对话复用同一个云函数与同一套约束 |
| 带上下文进对话 | `interview` 页 `onLoad` 已接 `storyId`／`sourceId`／`question`／`dimension` | 就地小忆传入当前章节与选中段落 |
| 「本章记忆」侧栏 | `book.wxml` 的 `data-action="memories"` | 卡住时可回看这一章的来源记忆 |
| AI 文字留痕 | `containsAiText`（与 `generationMode`、`handEdited` 分开记） | 就地生成的文字同样要留痕 |

**所以本需求的新东西只有三件**：一个常驻的小忆入口、一次「读当前内容 → 给一个问题」的
往返、以及把用户回答落回正文的路径（原话直接用，或请小忆整理）。

整理这一步也有现成的：`cloudfunctions/organizeMemory` 的提示词已经写明
「只能使用讲述者已经说出的事实，不得补造年份、地点、对白、心理活动或因果关系」，
正是 R9 需要的约束；`appendAiRevision` 已经让原话与整理版并存可回溯。
**两头都在，本轮主要是接线。**

## Problem Frame

**写作卡住和记忆卡住是同一件事，但产品把它们分在了两个页面。**

现在的路径：在 `book` 页写不下去 → 退出正文 → 进 `interview` 页 → 从头讲一遍
（`interview` 不知道你刚才写到哪） → 整理成片段 → 回 `book` 页 → 手动插入。
**中间四步都是流失点。**

需要解决的是三个具体问题：

1. **入口不在手边。** 小忆现在是一个页面，不是一个随时能按的东西。
   卡住时用户要做的第一个决定是「要不要离开我正在写的东西」，这个决定本身就会让人放弃。
2. **小忆不知道你在写什么。** 进 `interview` 页等于从零开始。
   用户已经写了三段，却要重新交代背景 —— 这正是「被审问」感觉的来源之一。
3. **聊出来的东西回不到正文。** 现在只能「整理成片段」再保存为记忆，
   然后在 `book` 页手动插入。用户想要的是「我说的这句话直接变成正文的下一段」。

同时要避免两个方向的做歪：

- **不能变成自动续写。** 默认行为是问一个问题，不是替他写下去。
  用户明确要求时可以代写，**但代写的原料只能是他刚说出的回答**（见 R9）——
  小忆整理他的话，不发明他的经历。区别在于：整理出来的仍然是他的事，
  续写出来的是小忆编的事。后者会毁掉这个产品的根基。
- **不能变成又一个聊天页。** 如果点小忆就跳到 `interview` 页，那只是把入口挪了个位置，
  三个问题一个都没解决。**必须在当前页面就地发生。**

---

## Actors

- **A1 写作者**：正在编辑记忆或章节正文的人。他随时可以点小忆，也随时可以不理它。
  他说出来的话是否进入正文，由他决定。
- **A2 小忆**：读用户当前正在写的内容（整段或选中的一段），
  给一个贴着这段内容的问题。用户明确要求时，可以把用户的回答整理成一段正文。
  **它不发明用户没说过的事** —— 整理的原料只能是用户的回答。
  任何写入正文都要经用户确认。
- **A3 家人**：不参与本流程。就地小忆只服务当前编辑者本人。

---

## Key Flows

**F1 记忆编辑中卡住（`interview` 页的保存阶段 / `personal-memory` 编辑）**
用户写了一半 → 点小忆 → 小忆读已写内容 → 给一个问题 →
用户口述回答 → 回答接在已写内容之后（原话保留，不改写）。

**F2 章节正文中卡住（`book` 页 `view === 'chapter'`）**
用户在正文编辑器里 → 点小忆（可先选中一段，也可不选）→
小忆读选中段落或当前章节 → 给一个问题 → 用户口述 →
生成一条 `ChapterEdit`（`kind: 'insert'`，anchor 在光标处）→
**对照展示 → 用户接受才写入**，并置 `containsAiText`。

**F3 不想聊，只想看看来源**
点小忆 → 选「看看这一章的记忆」→ 打开已有的「本章记忆」侧栏。
这条不消耗算力，也是卡住时最常见的需求。

## Requirements

### 入口

- **R1** 小忆入口在两处编辑界面常驻可见：`book` 页正文编辑（`view === 'chapter'`）
  与记忆编辑（`interview` 页保存阶段）。同一个视觉形象、同一个位置逻辑，
  用户不需要学两次。
- **R2** 入口**不抢注意力**：不跳动、不主动弹出、不在用户打字时出现提示。
  它只是一直在那里。用户不点，它什么都不做。
- **R3** 点击后**在当前页面就地展开一个小的对话标签**，**不得跳转到 `interview` 页**。
  **对话内容与正文必须同时可见**（2026-09-27 用户确认）：上半屏是正文，
  下半屏是对话标签，用户边看自己写的边回答问题。
  **不得沿用 `book` 页现有 panel 的做法** —— 现有的整理、历史版本等 panel
  是整块替换阅读区（`.reading-panel { flex: 1 }`），打开后正文就看不见了。
  对话标签可以收起成一条（只露最近一句问题），也可以拖高，但不能盖住整个正文。
- **R4** 展开后至少提供三个选择：**问我一个问题**、**看看这一章的记忆**、**关掉**。
  后两者不消耗算力。「关掉」要能一步完成。

### 小忆读什么

- **R5** 有选中文字时，以选中段落为主要上下文（照 `book.ts:767` 的
  `catchtouchstart` + `getSelectionText` 方式取，避免按钮抢焦点后读不到）。
  无选中时，以当前章节正文或当前记忆草稿为上下文。
- **R6** 上下文有明确上限并告知用户发送了什么。选中超过上限时提示少选一些
  （现有「发给家人」是 500 字上限，可参照但本场景可放宽）。
- **R7** 小忆**只读当前这一章或这一段**。不读其他章节、不读别人的记忆、
  不读家人的投稿。跨章节的连续性由既有 `characterContext` 机制处理，本需求不扩大范围。

### 小忆给什么

**默认给问题，但用户明确要求时可以代写。分界不是「能不能写」，而是「写的内容从哪来」。**

- **R8** 默认输出是**一个问题**，不是一段正文。
  必须与用户已写内容有可指出的语义联系（沿用 2026-09-25 需求 R4 的判据）。
  **不主动代写** —— 用户没要求时，小忆只问。
- **R9** 用户**明确要求**时，小忆可以代写，但只能整理**用户自己刚说出的话**。
  流程固定为三步，不可跳过中间那步：

  > 用户点「帮我写一下」→ 小忆**先在选中位置问一个问题** →
  > 用户回答 → 小忆把这个回答整理成一段正文交给用户。

  也就是说：**代写的原料只能是用户的回答，不能是小忆的想象。**
  没有回答就没有可写的东西；用户不回答，这一步就停在问题上。
- **R10 禁造边界（硬约束，任何模式都不放宽）** 整理时不得补造年份、地点、对白、
  心理活动或因果关系，不得替用户下结论或升华。允许保留不确定性。
  **直接复用 `organizeMemory` 已有的整理约束与提示词，不新建第二套。**
- **R11** 整理结果必须与用户原话**并存可回溯**：沿用 `appendAiRevision`，
  第一条 `spoken` 保留原话，整理版作为新 revision 追加。
  用户随时能看到自己原来说的是什么，也能退回去。
- **R12** 用户可以要求换一个问题。换问题不重新读取上下文、不重复上一个问题。
- **R13** 卡住时的问题应当**指向具体处**，而不是泛问。
  例如用户写到「那天很冷」就停住了 → 问「那天的冷你是怎么感觉到的」，
  而不是「还有什么想补充的吗」。
- **R14** 整理后的那段话，用户可以**直接改**。
  它是一个草稿，不是一个需要被接受或拒绝的判决。

### 回答怎么落回正文

- **R15** 用户的回答有三种落法，由用户选：
  **原话直接用**（不经整理）、**请小忆整理**（R9 的三步流程）、
  **自己复制一段**（对话里任何一段文字，包括小忆的问题和整理结果，都能长按复制，
  再粘到正文任意位置）。前两种要能一步选到；不要把整理做成必经步骤。
  **注意**：`interview` 页现有对话文字不可长按复制（未设 `user-select`），
  就地对话标签必须开启。
- **R16** 在章节正文中，无论哪种落法都生成一条 `ChapterEdit`（`kind: 'insert'`），
  经**对照展示 → 用户接受**才写入，沿用既有 `PendingChapterRevision` 机制。
  **不得就地替换或静默追加。**
- **R17** 接受后置 `containsAiText`（既有字段，只会置 true 不会退回）。
  原话直接用的那一路也置位 —— 对话参与了这段文字的产生，留痕从宽不从窄。
- **R18** 用户可以只聊不用：回答不进正文也是正常结束，不追问、不催促。
- **R19** 回答可以连续多轮。每一轮都能独立决定是否入正文、是否要整理。

### 可信与边界

- **R20** 小忆在就地场景同样遵守「暂停／只记录」意图识别
  （2026-09-27 已实现：`wantsPause` / `wantsRecordOnly`）。
- **R21** 模型不可用时，就地小忆走与 `interview` 页相同的本地问法，
  并按 2026-09-25 需求 R1 的修订判据用用户能懂的话说明状态。
  **模型不可用时不提供整理** —— 本地没有语义模型，不能假装整理过。
- **R22** 算力消耗与限额沿用 `textComputeUsage` 既有口径。
  「看记忆」「关掉」不计费。**注意整理是第二次模型调用**：
  一次「问题 + 整理」消耗两次算力，限额口径要按这个重算。
- **R23** 受保护的副本（`protectedCopy`）与只读场景不显示小忆入口，
  与现有工具条的 `wx:if` 条件保持一致。

## Acceptance Examples

**AE1（核心场景：只问）** 用户在章节里写到「那天屋里很冷，我妈在灶台前忙着」然后停住 →
点小忆 → 问「问我一个问题」→ 小忆问出一个与「冷」或「灶台」相关的问题 →
用户口述回答 → 对照展示 → 接受 → 这段话出现在正文里，是用户自己的话。
**不通过的样子**：用户没要求代写，小忆却输出一段替他写好的正文；
或问一个与这两句无关的问题。

**AE1b（核心场景：要求代写）** 同上位置 → 点小忆 → 选「帮我写一下」→
**小忆先问一个问题**（不是直接写）→ 用户回答「我妈那天在灶台前烙饼，我在旁边烧火」→
小忆整理成一段正文 → 对照展示 → 用户可直接改 → 接受后写入。
整理结果里只有「烙饼」「烧火」这些他说过的事。
**不通过的样子**：用户一点「帮我写一下」小忆就直接写出一段（跳过提问那步）；
或整理结果里出现他没说过的细节，例如凭空补出「灶台是土砌的」「那年是 1983 年」。

**AE1c（拒绝整理）** 用户回答完，选「就用我的原话」→
原话直接进正文，不经整理。**这一路必须和 AE1b 一样一步可选到。**

**AE1d（同时看见）** 对话标签打开时，正文上半部分仍可读、可滚动；
用户在对话里打字、键盘弹起后，**正文、对话、键盘三者同时在屏上**。
**不通过的样子**：打开标签后正文被整块盖住；或键盘弹起后正文消失
（本仓库 2026-09-11 修过同类问题，见 `docs/2026-09-11-keyboard-and-photo-display.md`）。

**AE1e（自己复制）** 用户长按对话里小忆整理出的一句话 → 复制 →
点正文某处 → 粘贴。**只要一句，不用整段接受。**

**AE2（选中段落）** 用户选中正文中的一句话 → 点小忆 →
问题针对**这一句**，不是整章。
**不通过的样子**：按钮按下后读不到选区（没用 `catchtouchstart`）。

**AE3（无选中）** 不选任何文字直接点小忆 → 以当前章节为上下文，正常给问题。
**不通过的样子**：提示「请先选中文字」而不给兜底 ——
移动端长按选中对年长用户本就困难。

**AE4（记忆编辑）** 在记忆编辑里写了一半 → 点小忆 →
问题贴着已写内容 → 回答追加在草稿之后，原话保留。
**与 AE1 的行为逻辑一致**，用户不需要学第二套。

**AE5（拒绝入正文）** 聊了两轮，用户决定都不用 → 关掉 →
正文无任何改动，无追问、无催促。

**AE6（只想看素材）** 点小忆 → 选「看看这一章的记忆」→
打开既有「本章记忆」侧栏 → **无算力消耗**。

**AE7（换一个问题）** 用户觉得问题不好 → 换一个 →
新问题不重复上一个，也不重新索取上下文。

**AE8（不打扰）** 用户连续打字十分钟不点小忆 →
入口全程无跳动、无弹出、无提示。

**AE9（模型不可用）** 断开在线 AI → 点小忆 → 给本地问法，
状态说明用用户能懂的话（不含「模板」「降级」这类词）。

**AE10（受保护副本）** 打开他人分享的受保护副本 → 不显示小忆入口。

## Success Criteria

1. **贴合率**：20 次真实卡住场景（章节 10 次、记忆 10 次），
   问题与用户已写内容有可指出的语义联系 **≥ 90%**。
   判据沿用 2026-09-25 需求 R4：能从原文里指出这个问题回应的那个词或意思。
   **人工评审，不接受 AI 自评。**
2. **零发明**：**这是硬门禁，出现一次就不算通过。**
   - 用户没要求代写时，20 次中 **0 次**主动输出正文草稿。
   - 用户要求代写时，整理结果中 **0 处**出现用户没说过的年份、地点、对白、
     心理活动或因果关系。逐句比对用户回答的原话。
   - **0 次**在用户还没回答时就先写出一段正文（跳过 R9 的中间那步）。
3. **落回可用**：用户接受的回答在正文中是他自己的原话，
   `containsAiText` 正确置位，历史版本可回溯。
4. **不打扰**：真机连续编辑 10 分钟，入口无任何主动行为。
5. **两处一致**：同一个用户在章节与记忆两处的操作步骤数相同、视觉位置一致。

### 明确不作为成功标准

- **测试通过数。** 前几轮反复出现「测试全绿、产品没变」。
- **小忆问得多深刻，或整理得多漂亮。** 本需求要的是「帮我想起来」和
  「替我把刚说的话收好」，不是「写得好看」。一个朴素但贴着原文的问题优于一个精彩但泛泛的问题；
  一段忠实于原话的整理优于一段文采更好但加了料的整理。
- **入口点击率高。** 点得多也可能意味着用户一直卡住。
  真正要看的是**点击后有多少比例的回答进了正文**。

## Scope Boundaries

### 本轮不做

- **不做自动续写、不做润色、不做改写已有正文。**
  代写仅限「整理用户刚才的回答」这一种，且需用户明确要求。
  不对用户已经写好的段落做改写或润色 —— 那是另一件事，本轮不做。
- **不跳转到 `interview` 页。** 那等于什么都没改。
- **不扩大上下文范围**到其他章节、其他人的记忆、家人投稿。
- **不新建对话规则。** 复用 `chatInterview` 的 12 条。
- **不新建写回机制。** 复用 `PendingChapterRevision` / `ChapterEdit`。
- **不改指纹算法**（`sourceFingerprint`）—— 改了会让已存书稿被判过期而隐藏正文。
- **不在只读或受保护副本里出现。**

### 明显不属于这个产品

- 主动提醒用户「你好久没写了」「这一章还差 200 字」。催促不是陪伴。
- 替用户判断哪段写得好、给文章打分。
- 把小忆做成通用助手（查资料、闲聊、写别的东西）。它只服务这一段回忆。

### 留给后续

- 语音口述（牵进音频链路，已有 `packages/audio` 分包可接）。
- 记录「用户在哪里卡住」并据此主动发现缺口 ——
  2026-09-25 需求已把这一层留给后续，且要求先把倾向跑准。
- 网页版「聊聊」的同类就地入口。两端定位不同，另议。

## Key Decisions

| 决定 | 理由与边界 |
|---|---|
| 一个机制覆盖两处编辑界面 | 用户原话「编辑记忆和编辑文章的时候都会有」。分别实现会得到两套不一致的行为 |
| 就地展开，不跳转 | 跳到 `interview` 页只是挪了入口，三个问题一个都没解决 |
| 默认只问，用户明确要求才代写 | 用户 2026-09-27 修正：「只是一个按钮的问题」。一刀切禁写会让卡住的人仍然卡住 |
| 代写的原料只能是用户的回答 | 分界不在「能不能写」，而在「写的内容从哪来」。先问、得到回答、再整理 —— 这样写出来的仍然是他自己的经历 |
| 整理复用 `organizeMemory` 的约束 | 那套提示词已经写明「只能使用讲述者已经说出的事实，不得补造年份、地点、对白、心理活动或因果关系」，正是本场景要的 |
| 原话与整理版并存 | `appendAiRevision` 已实现：首条 `spoken` 保留原话。用户随时能退回去 |
| 走 `ChapterEdit` 的提议→对照→接受 | 模型不确定，坏结果不能静默覆盖原文。机制已存在，不新建 |
| 复用 `chatInterview` 与 12 条约束 | 不新建第二套对话规则。一处改动两处生效 |
| 取选区用 `catchtouchstart` | `book.ts:767` 已证明这是避免按钮抢焦点的正确方式 |
| 只读当前章节/段落 | 范围越大越容易串味，也越贵。跨章连续性用既有机制 |
| 入口不主动打扰 | 主动弹出会让人觉得被监视和催促，与「温和」的产品调性冲突 |
| 「看看这一章的记忆」不消耗算力 | 卡住时最常见的需求其实是回看素材，不是要新问题 |

## Dependencies / Assumptions

- **依赖 2026-09-25 需求那一轮的成果**：模型必须真的在跑
  （三道发布开关）、追问必须贴着原话（R4/R5 已实现）。
  **如果那一轮的硬门禁没过，本需求无法验证** —— 就地小忆会继承同样的失配问题，
  而且因为它在正文里，失配会更刺眼。
- **依赖 `PendingChapterRevision` 现有机制**能承载单条 insert。
  **假设**它当前用于 AI 改写章节的路径可以复用；实施前确认。
- **依赖** `interview` 页的保存阶段有可插入的编辑区。
  **假设**记忆编辑的落回比章节简单（追加到草稿末尾即可）；实施前确认。
- **假设**用户在正文编辑器里能方便地选中一段话。
  移动端长按选中对老年用户可能困难 —— **这是需要真机验证的可用性假设**，
  所以 R5 规定了「无选中时用当前章节」作为兜底。
- **假设**就地入口会显著提高使用频率，因此 R19 要重新确认限额。
  现在的限额是按「进入对话页」这种低频行为定的。
- **已知风险：手机屏幕要同时放下三样东西。** 正文、对话标签、键盘。
  键盘通常占去近一半屏幕。本仓库已有键盘布局的正确做法：用 `onLoad` 捕获的实际窗口高度，
  键盘事件只扣一次（`adjust-position="{{false}}"` + `bindkeyboardheightchange`，
  见 2026-09-11 修复）。就地标签必须沿用，不要重新发明。
  **这一条只能真机验，模拟器调不出软键盘**（2026-09-11 文档已记录）。
- **已知风险：焦点离开正文后，插入位置会丢。** 用户在对话标签里打字时，
  正文编辑器会失焦。所以**打开标签的那一刻就要记下插入位置**，
  和 `book.ts:767` 在按钮抢焦点前先读选区是同一个道理。
- **已知风险**：`deepseek/deepseek-flash` 延迟中位数 7.08 秒、最长 12.52 秒（实测）。
  在正文里等 7 秒比在聊天页等 7 秒更难受，**需要明确的等待反馈**。

## Outstanding Questions

### 需要用户决定

- **小忆入口放在哪？** 工具条里多一颗按钮（和「照片」「保存」并列），
  还是正文右下角的悬浮图标？前者不遮正文但容易被当成普通功能，
  后者更像「随时在手边」但会挡住一行字。
- **卡住的问题要不要主动给？** 严格按 R2 是「不点就不出现」。
  但真正卡住的人可能连点小忆都想不起来。是否允许一种极轻的提示
  （例如光标停留很久后，入口轻微变化一次，且只一次）？
- **口述回答用什么方式输入？** 打字还是语音？这个产品面向年长用户，
  语音可能是更自然的方式，但会牵进音频链路（已有 `packages/audio` 分包）。

### 留给规划阶段

- 一次就地对话最多几轮，超出后是否引导去 `interview` 页做完整访谈。
- 记忆编辑与章节编辑的落回是否共用同一套确认 UI。
- 是否记录「用户在哪些位置卡住」作为后续「主动发现缺口」的素材
  （2026-09-25 需求已把那一层留给后续）。
