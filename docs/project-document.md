# 拾光家忆项目文档

## 一、项目背景

家庭对一位老人的记忆往往散落在不同人的聊天和讲述里。同一件事可能只有某个人记得，也可能出现彼此矛盾的版本。普通 AI 写作工具会把这些材料直接润色成故事，却很难回答“这句话来自谁”“本人是否认可”“哪里仍然记不清”。

拾光家忆希望先建立可信的家庭记忆链路，再写一本文字传记：亲人负责讲述，老人拥有事实确认权，AI 只负责整理已经确认的材料。

## 二、目标用户

- 仍能亲自讲述和确认经历的老人
- 与老人有情感连接、愿意补充回忆的亲人
- 发起传记、负责整理进度的家庭成员

## 三、本次作品范围

黑客松 MVP 完成以下文字闭环：

1. 亲人在聊天式家庭房间提交回忆；
2. 每段回忆保留投稿者和可见范围；
3. 老人逐条确认、拒绝或保留冲突；
4. 只有已确认且家庭可见的材料可以进入章节来源；私密投稿只对投稿者和老人可见；
5. 生成并预览传记第一章，同时展示事实来源。

真实跨设备邀请、微信身份、云数据库、语音、照片、正式隐私授权和内容安全不在当前完成范围内，演示时不得把它们描述为已实现功能。

## 四、技术栈

- 原生微信小程序：WXML、WXSS、TypeScript
- 微信本地存储：承载单设备黑客松演示状态
- 微信云函数：隔离模型密钥并提供可选的 AI 生成通道
- OpenAI-compatible API：只接收已经确认且家庭可见的来源材料
- TypeScript + Node.js 测试：验证事实权威和生成边界

## 五、核心创新点

### 1. 投稿而不是共同改稿

亲人只能追加自己的记忆，不直接覆盖他人说法或整本传记，从交互上降低家庭协作冲突。

### 2. 老人拥有事实确认权

每段材料先进入待核对状态。只有主人公本人可以把它确认为事实，发起者和 AI 都不能代替老人确认。

### 3. 冲突不会被 AI 自动抹平

“说法不一致”是一种被保留的正式状态。它不会进入权威正文，也不会被模型静默合并成一个看似确定的答案。

### 4. AI 降级透明

未配置云函数时，产品展示“本地演示草稿·未冒充 AI”，并只按来源整理材料。现场网络或模型服务失败不会让演示卡死，也不会伪装成真实 AI 输出。

## 六、技术流程

```text
家人文字投稿
  → 待老人核对
  → 确认 / 拒绝 / 保留冲突
  → 只筛选已确认且家庭可见的材料
  → 云 AI 生成或透明本地整理
  → 章节正文 + 来源列表
```
